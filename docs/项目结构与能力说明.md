# 项目结构与能力说明

本文档基于当前 `frontUI` 分支代码整理，目标是说明 `Agent_bio_react` 的项目结构、运行链路、已实现能力、当前边界，以及从专业开发视角给出的结构调整判断。

## 1. 项目定位

`Agent_bio_react` 是一个面向 Thermo BioPharma Finder 5.1 的桌面智能体项目。它不是传统固定脚本 RPA，而是围绕“任务文档 + 截图观察 + UI 解析 + 推理模型 + 桌面执行 + 视觉验证”的闭环运行。

当前已经具备两种入口：

- 命令行入口：直接运行 Python Agent。
- 桌面前端入口：打开 Electron 软件窗口，通过本地 FastAPI 后端启动和监控 Agent。

最近一次通过前端接入链路的实机运行已经完整通过，日志为：

```text
logs/20260514_170423.md
```

该轮执行结果为 `OK / Task complete / steps: 7`，耗时约 2 分 28 秒。

## 3. 核心运行链路

### 3.1 命令行链路

```powershell
cd F:\Agent_bio_react
python run_agent.py run --task biopharma_protein --reasoner deepseek --max-steps 30
```

执行流程：

1. `run_agent.py` 加载任务。
2. 创建推理器，例如 `DeepSeekReasoner`。
3. 启动或连接 OmniParser 服务。
4. 创建 Qwen 视觉验证 provider。
5. 创建 Maa Win32 桌面控制器。
6. 创建 `ReActAgent` 并进入主循环。
7. 输出控制台日志和最终 compact JSON。

### 3.2 桌面前端链路

```powershell
cd F:\Agent_bio_react
python -m agent_server

cd F:\Agent_bio_react\desktop_app
npm run start:desktop
```

前端启动后并不直接操作桌面，而是调用本地后端：

```text
Electron 前端
  ↓ HTTP / WebSocket
agent_server FastAPI
  ↓ subprocess
run_agent.py
  ↓
ReActAgent 主循环
  ↓
OmniParser / DeepSeek / Qwen / Maa Win32
```

这种结构的好处是：前端负责界面和交互，后端负责本地进程、文件系统、桌面自动化和日志落盘，两者职责清晰。

## 4. 本地后端 `agent_server/`

```text
agent_server/
├─ app.py                         # FastAPI 路由定义
├─ run_manager.py                 # Agent 子进程管理、状态、事件、日志落盘
├─ schemas.py                     # API 请求和响应模型
├─ __main__.py                    # python -m agent_server 入口
└─ __init__.py
```

当前接口：

```text
GET  /health
GET  /tasks
POST /runs/start
POST /runs/stop
GET  /runs/status
GET  /runs/events
WS   /runs/logs
```

职责说明：

- `app.py`：定义前端可以访问哪些接口。
- `run_manager.py`：真正启动 `run_agent.py`，读取 stdout/stderr，维护运行状态，写入 `logs/时间.md`。
- `schemas.py`：定义 `StartRunRequest`、`RunStatus`、`TaskInfo` 等结构。

当前日志策略：

- 每次 `/runs/start` 会按开始运行的系统时间创建日志文件。
- 文件名格式为 `YYYYMMDD_HHMMSS.md`，例如 `logs/20260514_170423.md`。
- 日志文件包含 run header、运行事件、stdout/stderr、status、summary。
- 前端日志页通过 WebSocket 实时接收事件，并通过 `/runs/events` 补拉，避免断线或错过开头日志。

## 6. Agent 核心 `agent/`

```text
agent/
├─ react_agent.py                 # ReActAgent 主循环
├─ failure_handler.py             # 失败上下文、失败策略、恢复决策
├─ task_loader.py                 # Markdown 任务加载
├─ task_parser.py                 # 任务步骤、窗口定义、动作序列提示解析
├─ runtime_logger.py              # 控制台日志和摘要格式化
├─ types.py                       # ImageInfo、UIElement、AgentAction、ToolResult 等核心类型
└─ __init__.py
```

主循环的核心步骤：

1. 根据任务窗口定义连接目标窗口。
2. 截图。
3. 调用 OmniParser 解析 UI。
4. 根据任务语义补充 synthetic 输入框或选择框。
5. 调用推理器生成 `actions`。
6. 执行动作序列。
7. 动作后同步窗口上下文。
8. 本地检测页面变化。
9. 调用视觉模型验证当前任务指示。
10. 成功则进入下一条任务指示，失败则交给错误处理层。

错误处理层当前策略是保守 v1：

- 失败发生后统一生成 `FailureContext`。
- `FailurePolicy` 决定是否重试当前节点、是否复用观察、是否降级验证、是否退出。
- 重试不是进入下一步，而是在当前任务节点内重试。
- 最近成功实机中没有触发错误处理决策。

## 7. 能力模块 `modules/`

```text
modules/
├─ reasoner/
│  └─ reasoner.py                 # DeepSeek / Manual / Scripted 推理器
├─ ui_parser/
│  └─ omniparser.py               # OmniParser 服务管理、API 调用、synthetic target
├─ vision/
│  ├─ providers.py                # Qwen / temporary vision provider
│  ├─ verifier.py                 # 视觉验证编排
│  ├─ page_change_detector.py     # 本地页面变化检测
│  └─ schemas.py                  # 视觉返回 schema
├─ memory/
│  └─ README.md                   # 占位说明
└─ api_keys.py                    # API key 读取
```

当前模型能力：

- 推理模型：DeepSeek V4 Pro。
- 视觉模型：Qwen `qwen3-vl-flash`。
- 本地页面变化检测：先用图像差异判断，必要时生成低清对比图交给视觉模型。
- 临时视觉 provider：用于测试或配置兜底。

推理器要求模型返回：

```json
{
  "actions": [
    {
      "action": "click",
      "index": 1,
      "coordinate": [100, 200],
      "text": null
    }
  ]
}
```

如果模型返回空 `content` 或无法解析为动作 JSON，会被归类为 `REASONER_FAILED`，并交给错误处理层。

## 12. 结构审查结论

### 12.1 当前不建议立刻大规模重构

当前项目刚完成前端接入、本地后端、日志落盘，并且通过前端实机跑通完整任务。此时大规模移动目录或重命名模块会带来较高风险：

- Python import 路径需要同步修改。
- Electron 调后端的 URL 和启动脚本需要重新验证。
- 实机自动化依赖本机窗口状态，回归成本高。

因此当前阶段更适合做文档归位、边界说明和小步拆分，不建议一次性重构全仓库。

### 12.2 当前命名基本合理

建议保留：

- `agent/`：表示智能体核心调度层，名称准确。
- `agent_server/`：表示本地 Agent 后端服务，当前职责明确。
- `desktop_app/`：表示桌面端前端工程，名称清楚。
- `tasks/`：任务文件目录，清楚。
- `tools/`：桌面操作工具适配层，当前可接受。
- `tests/`：测试目录，标准。

可以后续再评估：

- `modules/` 名称偏泛。如果后续模块继续增多，可以考虑改为 `integrations/` 或拆成更明确的 `reasoning/`、`vision/`、`ui_parsing/`。
- `tools/` 如果未来不仅有 Maa，也有其他执行器，可以改为 `executors/` 或 `desktop_control/`。
- `agent_server/` 如果未来承载更多 API、配置管理、用户会话和打包服务，可以改为 `backend/`。

这些不是当前必须改的点。

### 12.3 当前最应该整理的是文档归位

旧版根目录 `项目结构与能力说明.md` 已经落后。新的项目结构说明应以本文档为准：

```text
docs/项目结构与能力说明.md
```

根目录更适合放一个短 `README.md`，说明项目是什么、怎么启动、怎么验证，而不是长期放大型结构说明。

## 14. 当前边界和风险

当前仍存在这些边界：

- 前端尚未打包成单个 `.exe`。
- Electron 不会自动启动 Python 后端。
- 前端模型设置页还没有真正写入后端运行配置。
- 前端窗口预览仍是模拟 UI，不是真实截图流。
- `App.tsx` 和 `run_manager.py` 后续需要拆分。
- 推理稳定性仍依赖 DeepSeek 按协议返回 `actions` JSON。
- 视觉验证依赖 Qwen API。
- OmniParser 默认使用项目内相对目录 `OmniParser/`，也可通过 `OMNIPARSER_ROOT` 覆盖。
- 实机运行受 Windows 桌面状态、Thermo 窗口状态和文件选择窗口状态影响。

## 15. 推荐后续结构路线

建议按以下优先级推进：

1. 保持当前目录结构，不做大规模重命名。
2. 将 `docs/项目结构与能力说明.md` 作为结构说明源文档。
3. 新增根目录 `README.md`，只放最短启动说明和入口链接。
4. 前端稳定后拆分 `App.tsx`。
5. 后端稳定后拆分 `run_manager.py`。
6. 让 Electron 自动拉起 `agent_server`。
7. 增加桌面端打包方案，例如 `electron-builder`。
8. 再考虑是否把 Python 后端一起封装进安装包或便携包。
